Read first

Launch principles

Never promote staging WorkOS identities. Production and staging are isolated. Do not copy staging workos_user_id values, API keys, client IDs, users, provider connections, or sessions into production.
  • The production callback must be one exact HTTPS URL on a controlled domain.
  • The WorkOS production API key belongs only in the production secret manager.
  • Existing production users begin with a null workos_user_id and link explicitly.
  • The nullable database column may remain after an application rollback.
  • Keep existing Fortify authentication available throughout the launch.
Gate 0

Go/no-go prerequisites

  • The implementation is reviewed, committed, pushed, and identified by a release tag or immutable commit.
  • Automated tests, PHPStan, Pint, frontend build, and dependency audit pass for the release candidate.
  • Google, GitHub, account linking, cancellation, TOTP, and WorkOS step-up confirmation pass end to end in staging.
  • Production DNS and TLS are active and APP_URL uses the final HTTPS origin.
  • A restorable production database backup exists and its restoration procedure is known.
  • The prior known-good application release is available for immediate redeployment.
  • Application, database, WorkOS, and rollback owners are present for the cutover window.
No-go: stop if any prerequisite is incomplete. Do not compensate by pointing production at the staging WorkOS environment.
Phase 1

Prepare WorkOS Production

  1. Open the production environment in the WorkOS Dashboard and unlock it with billing information.
  2. Create the production application or select its default application.
  3. Generate the production API key. Save it immediately; production keys are displayed once.
  4. Record the production Client ID.
  5. Add the exact redirect URI below and make it the application default:
https://YOUR-PRODUCTION-DOMAIN/auth/workos/callback
  • Production environment unlocked.
  • API key stored in the production secret manager and nowhere else.
  • Production Client ID recorded.
  • Exact HTTPS callback configured with no production wildcard.
  • Production application homepage points to the correct HTTPS origin.
  • Production logo, colors, support links, and displayed application name are correct.
Phase 2

Configure the AuthKit session policy

In WorkOS Production → Applications → WhatsForDinner → Sessions, use these initial values:

SettingInitial valuePurpose
Maximum session length7 daysHard limit before AuthKit requires authentication again.
Inactivity timeout24 hoursExpires an AuthKit session that has not been used.
Access token duration5 minutesLimits the callback token used immediately by WhatsForDinner.
Important: the Laravel session remains the application authorization session. WorkOS expiry does not currently revoke an already-running Laravel session. Security settings still force fresh AuthKit reauthentication with max_age=0 and validate auth_time.
  • Maximum session length configured.
  • Inactivity timeout configured.
  • Access-token duration configured.
  • Final values recorded in the change ticket and monitoring plan.
Phase 3

Configure production OAuth providers

Google

  • Production OAuth application, consent screen, branding, authorized domains, Client ID, and Client Secret configured.
  • The redirect URI supplied by WorkOS is registered at Google exactly.
  • Google enabled in WorkOS Production.

GitHub

  • Production GitHub OAuth application has the correct homepage, callback supplied by WorkOS, Client ID, and Client Secret.
  • GitHub enabled in WorkOS Production.
Provider scope: Apple and all other social providers must remain disabled in both WorkOS staging and production.

Phase 5

Deploy in controlled order

  1. Place the application in the platform's maintenance or controlled-release state if atomic migration-before-traffic is unavailable.
  2. Deploy the reviewed immutable release.
  3. Install production dependencies and build assets.
  4. Run the database migration before the new UI receives traffic.
  5. Rebuild Laravel caches and restart long-running workers.
  6. Restore controlled access for smoke testing.
composer install --no-dev --classmap-authoritative
npm ci
npm run build
php artisan migrate --force
php artisan optimize
php artisan queue:restart
  • Application release deployed successfully.
  • workos_user_id migration completed successfully.
  • Laravel production caches rebuilt.
  • Long-running workers restarted.
  • Application, database, cache, queue, and mail health checks green.

Phase 6

Open access and monitor

  • Invitation, verification, and password-reset email delivery monitored.
  • Support owner has collision, linking, cancellation, and provider-outage guidance.

Rollback

Rollback triggers and procedure

Trigger rollback when

  • Existing password, passkey, TOTP, or recovery-code login is impaired.
  • Users are linked to the wrong local account or can bypass explicit linking.
  • Security confirmation can be bypassed or confirms a different identity.
  • Callbacks permit external redirects, replay, or state mismatch.
  • Provider failures create widespread login denial without an acceptable fallback.
  • Sensitive credentials, tokens, or authorization codes appear in logs or responses.

Procedure

  1. Declare rollback and timestamp it: ________________________________
  2. Disable affected OAuth providers in WorkOS Production if provider-specific containment is sufficient.
  3. Redeploy the previous known-good application release.
  4. Do not roll back the nullable workos_user_id migration during the incident; older code safely ignores it.
  5. Preserve logs and database evidence without copying secrets or tokens into the incident record.
  6. Verify existing Fortify login, dashboard access, and logout after rollback.
  7. Notify stakeholders and open an incident review before retrying launch.
